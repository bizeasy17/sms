# metrics 评分结果持久化与检索需求

## 1 文档信息

- 模块：`manniu_backend/metrics`
- 文档状态：需求提案，待接口与字段评审
- 配套设计：[backend-design.md](backend-design.md)
- 评分算法基线：[metrics-backend-design.md](../modules/metrics-backend-design.md)
- 范围：常规财务六维、TopN 特征六维、企业增长潜力信号（CGPS）结果的持久化、历史留存与检索
- 非目标：本文件不授权直接变更 API、PostgreSQL schema、评分算法或前端页面

## 2 背景与目标

三类评分目前由不同计算逻辑产生，结果需要可追溯地落库，支持按证券、评分类型、时点、状态和分数检索，并可查看维度及因子证据。持久化不得把不同算法合并成同一维度定义，也不得以缺失值补分掩盖数据状态。

## 3 用户与使用场景

1. 用户按证券代码或名称查询某一类评分的最新有效结果。
2. 用户按评分类型和 as-of 日期范围检索历史快照，比较不同计算版本的结果。
3. 用户按总分区间、状态或指定维度分数筛选结果，并查看七维/六维分项及证据。
4. 运维或分析人员追溯一次结果使用的算法版本、财报期、公告时点、模型清单及同行映射版本。

## 4 功能需求

### 4.1 支持的评分类型

| 稳定类型键 | 展示名称 | 结果维度 | 类型专属追溯信息 |
| --- | --- | --- | --- |
| `FINANCIAL_HEALTH_6D` | 常规财务六维 | 六维；保留当前 profile 实际输出键 | scoring/profile 版本、报告期和 as-of 快照日 |
| `MODEL_TOPN_6D` | TopN 特征六维 | 六维；保留模型映射键及特征明细 | model/report type、model scope、feature set、TopN 参数、mapping/normalization 版本及降级状态 |
| `COMPANY_GROWTH_POTENTIAL` | 企业增长潜力信号（CGPS） | 固定七维 | calculation/profile/peer mapping 版本、as-of、报告期、公告日、peer 范围和覆盖率 |

类型键用于区分结果语义；不同类型的同名维度或总分不可视为同一算法结果。常规六维当前 profile 可能使用类型专属 key，持久化不得强制改写为 TopN 或 CGPS 维度键。

### 4.2 持久化与历史

1. 每次可追溯计算产生一个评分快照，包含证券、评分类型、as-of 日期、财务报告期（适用时）、总分/标签/状态、覆盖情况及算法 provenance。
2. 维度分、维度权重、可用状态及其因子/特征证据必须可随快照读取；保留不可用、部分可用及缺失原因，不将缺失转换成 0 或 50。
3. 保存类型专属元数据。TopN 保存模型与特征清单版本、计分/候选数量和降级状态；CGPS 保存同行范围、样本数、公告时点及回退状态。
4. 历史快照可查询，不因重算而覆盖已发布的不同算法版本或不同输入快照。主表以 `(security_id, score_type, input_fingerprint)` 复合唯一约束保证幂等。
5. 后端存储必须使用 PostgreSQL；评分写入只由受控 metrics 计算/刷新流程触发，不在查询请求中回源外部数据或重算历史事实。

### 4.3 搜索与查询

查询能力至少支持：证券代码精确匹配、名称匹配、评分类型、as-of 日期范围、财务报告期、状态、总分区间、标签，以及维度键和维度分区间。列表需分页、排序，并默认按 as-of 日期及创建时间倒序；详情需返回完整维度与证据。

查询只读已持久化结果，不隐式触发评分计算。响应应携带评分类型和算法版本，阻止调用方把不同类型或不同版本的分数直接混排而不知情。具体 URL、字段名称、默认排序和权限范围见设计提案，编码前须确认。

### 4.4 手工入库 CLI

提供 Django management command 手工计算并持久化指定评分类型。CLI 支持 `--scope ts-codes|all`；`ts-codes` scope 接收一个或多个证券代码或证券文件，`all` scope 选择证券主表中的股票。命令要求指定 as-of 日期和评分类型，并提供只计算、不写库的 dry-run；`--batch-size`（默认 100）控制每批证券数，批次开始/完成输出处理区间、累计进度、结果计数和耗时。选择 TopN 时可指定 report type、model version、score_topn 和 store_topn。命令输出每类评分的成功、跳过、失败和幂等命中汇总，存在失败时返回非零退出码。具体 command 名称和证券文件格式由后端设计确认。首期不自动加入 daily job；后续另行接入并明确调度和失败重试策略。

## 5 数据质量与安全要求

1. 同一快照中的证券、评分类型、时点、来源期、维度和证据应保持关联一致；异常或不完整结果可以保存诊断状态，但不得伪装成有效总分。
2. 日期时点遵循各评分算法的 as-of 语义；CGPS 只能使用公告时点不晚于 as-of 的财报版本。
3. 查询遵循现有 API Gateway 认证、授权和分页约定；不得泄露其他用户私有数据（如果后续评分结果被定义为用户私有）。
4. 不新增自动交易、买卖建议或资金操作能力。

## 6 验收标准

1. 三种评分类型可以分别写入、查询和识别；结果不会互相覆盖，维度键保持各自算法语义。
2. 对同一评分快照可读取总结果、全部维度和因子/特征证据，并能还原算法及数据 provenance。
3. 支持第 4.3 节列出的过滤、排序和分页；筛选维度分数不会把缺失分数当成 0。
4. 相同证券、评分类型和输入指纹重复持久化满足幂等；不同证券、评分类型、版本或输入指纹的历史结果均可保留和区分。
5. CLI 可针对三类评分执行 dry-run 和真实持久化；失败有逐类统计且整体退出状态可供批处理判断。daily job 集成不属于首期验收。
6. 无结果、低覆盖、部分维度、CGPS 金融企业不适用、TopN provider 降级等状态可被查询方识别。

## 7 测试用例定义

1. 分别持久化常规六维、TopN 六维和 CGPS 结果，断言类型键、维度键和类型专属版本元数据正确。
2. 对含缺失维度/因子的结果执行保存和详情查询，断言缺失状态及原因保留且没有被补成 0/50。
3. 重复提交相同证券、评分类型和输入指纹，断言复合唯一约束幂等；改变任一键成员，断言可保存不同快照。
4. 组合证券、评分类型、日期、状态、总分和维度过滤查询，验证结果、分页边界及排序稳定性。
5. 查询不存在的证券/快照、非法筛选值、无效日期范围和不适用/降级结果，验证明确的空结果或校验错误，不触发重算。
6. 验证 CLI dry-run 不写库、真实运行正确统计结果，并在部分证券失败时返回非零退出码。
7. 验证 PostgreSQL 复合唯一约束、索引及并发幂等写入；不以 SQLite 代替持久化验证。
