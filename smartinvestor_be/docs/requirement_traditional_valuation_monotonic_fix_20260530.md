# 需求变更说明：传统估值低估分非单调修正（002236.SZ 案例）

## 1. 背景
- 当前传统估值评分逻辑中，核心方法（PE/PB/PS）存在按“当前价 * 上下界倍数”进行硬过滤的机制。
- 实测在 `002236.SZ` 最近交易日中出现：股价下跌后，`undervalue_score` 从 97 降到 79，`buy_candidate` 从 `True` 变为 `False`。
- 该现象与“价格下跌应不降低低估程度”的业务直觉冲突，且会引发用户对信号稳定性的疑问。

## 2. 目标
- 在不引入预测信号依赖的前提下，仅修正传统估值口径内的评分稳定性。
- 避免因核心方法临界剔除导致的分数/买点断崖式跳变。
- 保留传统估值对极端离群值的防护能力（不放开为无限制纳入）。

## 3. 变更范围
- 仅涉及后端传统估值汇总逻辑：`valuation/services/valuation_summary.py`。
- 不改动预测信号接口与策略，不改动前端展示协议字段名。

## 4. 拟实施方案（V1）
1. 将核心方法硬过滤改为软过滤降权：
- 当前：超过上下界直接剔除。
- 目标：超过上下界时降权参与（权重衰减），避免方法集合离散跳变。

2. 保持 buy_candidate 规则结构不变：
- 仍基于核心方法数、低估方法数、复合/保守收益阈值判断。
- 但核心集合判定由“硬剔除后集合”改为“软过滤后有效集合”。

3. 新增分数稳定性护栏（轻量）：
- 针对同一股票连续交易日，若仅由核心方法阈值切换导致评分骤降，限制单日异常降幅。
- 护栏只作用于传统估值分，不影响原始估值价计算。

## 5. 验证方案
1. 单票回放验证：`002236.SZ` 最近 30 日。
- 输出对比：`close`、`old_score`、`new_score`、`old_buy`、`new_buy`。
- 重点检查 2026-05-28 -> 2026-05-29 是否消除反向跳变。

2. 小样本回归验证：
- 抽取若干高波动股票，检查是否出现大面积“全部顶格 100 分”的过度宽松现象。

3. 行为一致性验证：
- 返回字段保持兼容：`undervalue_score`、`buy_candidate`、`composite_valuation_price`。

## 6. 验收标准
- 002236.SZ 示例中，不再出现“价格下跌但低估分显著下滑并失去买点”的突兀反向行为。
- 不引入预测侧逻辑，不改变 API 字段结构。
- dry run 输出可复现且有明确对比证据。

## 7. 风险与回滚
- 风险：评分可能整体抬升，需要控制“满分挤压”现象。
- 回滚：保留旧规则分支，可通过配置开关切回硬过滤逻辑。

- T2：接入 buy_candidate 统计口径并保持兼容。

- T4：输出对比结果并确认是否推广至 UAT。

## 9. 第三阶段调优（V3）

### 9.1 问题补充
- V2 已修复 `002236.SZ` 的反向跳变，但在横向样本中出现部分股票 `old_buy=True -> new_buy=False` 的集中翻转（典型如 `600036.SH`）。
- 现状下 `core_under_methods` 仅按硬过滤后核心集合统计，导致“被软纳入核心”的方法不参与核心低估计数，可能在临界日产生过严判定。

### 9.2 V3 方案
1. 新增“软纳入核心低估计数”门槛：
- 仅对已进入 `effective_core_methods` 且权重达到新阈值的方法，允许计入 `core_under_methods`。
- 保持硬过滤通过的方法优先，软纳入仅作连续性修复，不放开为无限制纳入。

2. 新增配置参数（默认保守）：
- `BUY_CANDIDATE_CORE_SOFT_UNDER_MIN_WEIGHT`：软纳入方法计入 `core_under` 的最小权重阈值（默认 0.98）。

3. 不改变 API 输出字段与评分基础结构：
- 仍返回现有字段：`undervalue_score`、`buy_candidate`、`composite_valuation_price`。
- 仅调整 `buy_candidate` 中 `core_under` 的计数口径，并在 reason 中标注软纳入明细。

### 9.3 V3 验证与验收
1. 必须继续保持：`002236.SZ` 关键日修复成立。
2. 对已观测翻转样本，优先降低 `old_buy=True -> new_buy=False` 的集中翻转天数。
3. 不出现明显“全面放宽”现象：
- 30 日样本内新增 `old_buy=False -> new_buy=True` 的比例应可解释且集中在临界日。
4. 若结果可接受，再进入 DEV->UAT 同步流程。

## 10. 第四阶段改造（V4）：快照刷新判定收口

### 10.1 问题定义
- 当前 `valuation/services/valuation_summary.py::summarize_buy_candidate` 已作为前台实时信号判定主函数。
- 但快照刷新命令（`prediction/management/commands/prefillvaluationsnapshot.py`）中的信号/分值口径未与该函数完全统一，导致历史回看与前台实时信号可能出现口径漂移。

### 10.2 目标
1. 快照刷新阶段生成的 `buy_candidate` 与 `undervalue_score`，统一使用 `summarize_buy_candidate` 判定。
2. 前台实时接口与快照刷新在同一输入条件下得到一致结果。
3. 保留现有 API 字段兼容，不引入破坏性字段变更。

### 10.3 实施方案
1. 在 `prefillvaluationsnapshot.py` 引入并复用 `valuation_summary.summarize_buy_candidate`。
2. 将快照刷新中的方法集合构建为标准 `method_map` 后统一传入该函数，写回分值与买点结果。
3. 对口径分叉位置新增最小审计信息（如判定来源标记），便于后续排查。

### 10.4 非目标
- 不改动估值引擎本身的估值价计算（`test_valuation_light/get_stock_valuation_snapshot`）。
- 不在本次变更中重构前台所有请求参数，仅聚焦判定收口与结果一致性。

### 10.5 验证方案
1. 单票一致性验证：`002236.SZ`，`asof=2026-05-26`，`Q1`。
- 对比“快照刷新结果信号”与“前台接口信号”在同一方法集合下是否一致。
2. 多票抽样验证：至少 60 只股票，15 日窗口。
- 指标：`old_true_new_false` 不增加，翻转率不异常放大。
3. 回归验证：确保现有字段结构与下游读取流程不报错。

### 10.6 验收标准
1. 快照刷新与前台实时在同口径输入下，`buy_candidate` 与 `undervalue_score` 一致。
2. 不引入新的 API 兼容性问题。
3. 对 002236.SZ 关键日期不再出现由判定路径差异导致的异常跳变。
